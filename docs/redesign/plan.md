Written before any deletion, so the numbers below are the state the work starts
from. If a figure here disagrees with the repo later, this file is the record of
what was true when the work began.

## 2. What "all UI code" covers

Measured by file and line count, excluding `board-mcp/` (the user's own project,
out of scope). This figure has been wrong twice and the corrections are recorded
rather than quietly absorbed, because a deletion set that is 38% too large
deletes behaviour:

1. a first pass counted 57,000 lines, because it swept in built bundles;
2. the second pass counted 369 files and 17,350 lines, which was still too large
   for a different reason — it took whole *directories* as UI. The classification
   in `auxiliary-hosts.md` then found that `apps/mantis/src/hosts/dingtalk` (34
   files), `packages/effect-interface` (12) and all but four of the `ui-*` files
   (32) are **behaviour that happens to live beside a UI**, and they left the set;
3. the third pass counted 231 files and 11,399 lines, and was wrong a third time
   for the same reason one layer down: it took `packages/effect-ui` as a whole.
   Reading that package file by file then found 22 of its 36 files are the
   contract, the validation and the server-side lowering, with three named
   non-presentational call sites keeping them alive;
4. the figure below is the deduplicated union of the five groups, counted on one
   basis: hand-written source, tests excluded, generated bundles excluded.

| group | files | lines |
|---|---|---|
| A · the console client, `apps/effect-server/src/client` (less tests) | 55 | 2,741 |
| B · the nine apps' view declarations, `apps/*/src/effect-ui*.ts` | 73 | 3,918 |
| C · `packages/effect-ui/src` — the 10 presentation files plus the 4 with no consumer at all | 14 | 570 |
| D · renderers inside packages that survive (`ui-renderer/src/*`, `ui-runtime/src/json-render.ts`) | 4 | 222 |
| E · auxiliary presentation (`mantis/src/hosts/webui/panel`, board `web/public`, `deckconsole/public`) | 63 | 2,708 |
| **union** | **209** | **10,159** |

Each correction moved in the same direction, and the reason is the same each
time: a directory is not a unit of intent. The number fell from 57,000 to 17,350
to 11,399 to 10,159, and every step removed files that only *looked* like UI from
a directory listing.

Two files under `apps/mantis/src/hosts/webui/public/` (`app-shell.js`,
`app-shell.css`, together ~40k lines) are build artifacts of `panel/`. They are
regenerated, not hand-deleted, and are excluded from the count above.

`apps/effect-server/public/effect-ui-client.{js,css}` is likewise a build
artifact, regenerated by `bun run --cwd apps/effect-server build:client`.

What group C leaves standing was the one genuinely open question, and it is
resolved file by file in §4: 22 files survive on three named non-presentational
call sites, and that resolution is what makes the union above final.

## 3. The proofs this invalidates

Thirteen modules under `formal/Formal/` name a UI file in their header. A module
whose modelled file is deleted proves a property of nothing, so each one goes
with its file unless the file is kept.

**This table was first written from the module names and was wrong in both
directions.** It sent `Derive` to the "goes" band when it is fully live, and it
sent `Entry`, `Refresh` and `Readout` to the same band when each is half live —
half their theorems are stated about a file that survives. It was then read
module by module, definition by definition, and corrected. The correcting
question is not "does the module have a UI word in its name" but **"what does it
prove, and does the thing it proves still exist"**:

| module | what it actually proves | disposition |
|---|---|---|
| `Adapt.lean` | React handler/prop wiring (`attributes`, `read`, `wired`) for the conversion layer | **goes** — 13 theorems about a deleted file |
| `Stack.lean` | browser history (`backTarget`, `canGoBack`, `reconcile`) | **goes** — pure navigation, no surviving consumer |
| `Screen.lean` | `walk`/`chainOf` soundness and termination (`mem_chainOf`, `walk_eq_nil_iff`, `walk_link`) | **stays** — see the `chainOf` note below |
| `Chain.lean` | `chainOf` repeats no screen and no id (`chainOf_nodup`, `chainOf_ids_nodup`) | **stays** — same subject as `Screen.lean` |
| `Derive.lean` | id minting (`slug()` at `screen-derive.ts:50-56`, the `[ROOT_SCREEN]` seed at `screen.ts:38`) | **stays** — fully live. The first table had this backwards. |
| `Door.lean` | the gate path is the send path; two doors of one press differ only in what they carried | **stays, re-pointed** — nothing it names survives, but the rule binds the new runtime |
| `Entry.lean` | `onEnter` and address half is real (`unaddressed_iff`, `the_screen_is_handed_what_the_press_held`); the press/write half is the deleted runtime | **stays, half re-pointed** |
| `Refresh.lean` | `clear`/`refresh` store semantics (`answer_survives_refresh`, `refresh_never_blanks`) are real; the editor half is the deleted runtime | **stays, half re-pointed** |
| `Readout.lean` | 6 theorems model `sourceStateOf` at `source-status.ts:48`; 4 model the deleted `readout.ts` | **split** — keep 6, delete 4 |
| `Timeline.lean` | turn numbering onto durable history | **stays** — both files are behaviour (§4) |
| `CardVerdict.lean` | the verdict is read only from fields named `action` | **stays** — the file is behaviour |
| `Lifecycle.lean` | register and dispose are symmetric; a stale disposer cannot revoke its replacement | **stays** — behaviour (§4) |
| `ToolKey.lean` | a dot-free interface id splits a flattened key into the pair that built it | **stays** — behaviour (§4) |

**`chainOf` is kept deliberately.** Its only runtime consumer today is
`client/effect-ui-screen-nav.ts`, which is presentation and goes. The
reimplemented client needs it anyway: a cold link into a screen has to rebuild
the ancestor stack from each screen's declared `parent`, and that walk is exactly
`chainOf`. Keeping it is what keeps `Screen.lean` and `Chain.lean` proving
something real, and deleting it to save eight theorems would mean re-deriving the
same walk, unproved, in the new client.

So the corrected figure is **460 theorems in 55 files**: 493 less the 13 dead
`Adapt` theorems, the 16 dead `Stack` ones, and the 4 `Readout` theorems that
model a deleted file. The reimplementation is obliged to prove its own mechanisms
and to bring this back up; that obligation is the house rule and is not waived by
a redesign.

Three modules are kept with a debt attached, and the debt is not optional:
`Door`, `Entry` and `Refresh` keep their headers naming a file that will be gone
until the layer that replaces it lands. A module header names the file it models,
so leaving it stale is the same defect as proving nothing, and §7 puts the
re-pointing in the layer that creates its new subject rather than at the end.

A fourteenth module, `Rollup.lean`, models `board/src/tasks/rollup.ts` —
behaviour, which stays — but the only two files that *read* the rule it proves
(`board/src/hosts/web/public/state.js:13`, `tree-view.js:48-54`) are presentation
and go. The module keeps its proof; the reimplementation is obliged to consume
that rule again rather than re-derive it in the view.

## 4. What is not presentation, and therefore stays

A file is presentation when its job is to draw or to navigate a surface.
It is **not** presentation when it decides who may do something, stores
something, parses a payload, or carries a transport — even when a UI reaches it.
Those keep their files and their proofs.

**Established, per file, in `auxiliary-hosts.md`** (178 files classified):
**62 presentational, 116 non-presentational.** The result is lopsided in a way
worth stating plainly, because it shrinks the deletion by more than half:

- Only two directories are mostly presentation — `mantis/src/hosts/webui/panel`
  and `board/src/hosts/web/public`.
- The DingTalk host, the MCP hosts, and all eight `ui-*`/`effect-interface`
  packages are **behaviour that merely lives beside a UI**. Not one file under
  `apps/mantis/src/hosts/dingtalk` is presentation: the card's look is a template
  in the DingTalk console, not here.
- Four of the surviving files are pinned by Lean proofs (`CardVerdict`,
  `Timeline`, `ToolKey`, `Lifecycle`), which is the §3 result reached from the
  other direction.

One consequence the deletion must respect: `ui-renderer/src/index.ts`,
`ui-renderer/src/json-react.ts`, `ui-renderer/src/theme.ts` and
`ui-runtime/src/json-render.ts` are presentation *inside packages that stay*. They
are a second renderer for the same node vocabulary the console's `adapt/` layer
renders — two ways to draw one spec, which is the same defect as four UIs. The
reimplementation resolves them against the one surface rather than leaving both.

Files marked *uncertain* in `auxiliary-hosts.md` (a barrel that re-exports a wire
limit, a client store's filter rule, a test channel) were resolved conservatively:
a file that decides a value or a transport is kept even when a UI reads it. Re-
reading one later costs less than deleting behaviour and then proving nothing
about it.

**`apps/effect-server/src/console/` (5 files) + `console-plugin.ts`**, resolved
here because it is the console's own server half and neither inventory covered
it. `console-plugin.ts` (64 lines) registers the console's routes on the plane
and carries the bundle: transport, **kept**. `apps-catalogue.ts` (37) decides
which apps have a view; `config-route.ts` (35) reads and writes configuration
payloads; `tools-route.ts` (69) is the MCP tool inspector's API; `options.ts`
(15) is the app's own options. All four decide a payload or a setting rather than
draw one: **kept**. Only `view-route.ts` (45) goes — it lowers a declared view to
a `@json-render` spec, which is the server half of the render contract, and the
render contract is what the redesign replaces.

That deletion has a consequence worth stating before it is made: `view-route.ts`
is the **only** place in the repository that computes `jsonSpec`. The console
client cannot lower a view itself, because the browser bundle does not carry the
lowering. So the replacement lowerer has to land with the client that consumes
it, or the console has a payload with no producer. This is why the deletion and
the reimplementation are one act per layer rather than two acts.

### `packages/effect-ui` — 36 source files, resolved one by one

This is the one area that is genuinely mixed, and it decides the fate of six
other files, so it was settled by reading each file and each of its consumers
rather than by the directory it sits in.

**22 survive**, each on a named non-presentational consumer:

| file | the consumer that keeps it |
|---|---|

| `screen-spec.ts` | `Entry.lean:2` — `UiScreen.onEnter` |
| `data-spec.ts` | `Refresh.lean:2` — `UiActionSpec.clear`/`.refresh` |
| `value-spec.ts` | `schema.ts:12` |
| `contract-types.ts` | `projector.ts:8` |

| `json-spec.ts`, `json-values.ts` | `view-route.ts:16` — `viewToJsonSpec` |
| `form-spec.ts` | `config-route.ts:17` — `formToJsonSpec` |

**10 go as presentation**: `nodes.ts`, `empty-rows.ts`, `html-renderer.ts`,
`region.ts`, `readout.ts`, `form/mount.ts`, `form/render.ts`, `form/controls.ts`,
`row.ts`, `press.ts`.

**3 more go, as dead code rather than as presentation**: `ui.ts` (`defineUi`),
`renderer.ts` (`UiRenderer`) and `document.ts` (`specOf`/`htmlOf`/`languagesOf`)
have no consumer anywhere. Dead code is not "the contract the apps declare
against", and CLAUDE.md's no-backward-compatibility rule deletes it.

The whole non-presentational surface of the package is **three call sites**:
`viewToJsonSpec` + `screensOf` (`console/view-route.ts:16,34`), `formToJsonSpec`
(`console/config-route.ts:17`), and `makeRenderContract` + `contractTo*`
(`monitor/projection.ts:19,21`). Nine other importers are `import type`-only and
use `EffectUiView` as the value type of the `uiViews` map.

**One ruling is needed, because §4's four tests do not cover it.** `json-spec.ts`
neither authorizes, nor stores, nor parses, nor transports: read literally, §4
says it is presentational and goes. It must not. Lowering a declaration into a
renderer's input stays **server-side**, for two reasons that are not stylistic.
`apps/effect-server/src/console/view-route.ts` is its only caller, and the client
bundle does not carry the lowerer; `effect.boundary.json:3` exists precisely to
enforce that boundary, and moving the lowering into the browser takes the client
bundle from 2.46 MB to 5.0 MB. So §4 is extended here:

> A file is also **not** presentation when it lowers a declaration into the input
> a renderer consumes, if the lowering is what keeps the renderer's dependency
> out of the client.

This is the same rule as "carries a transport", applied to a payload instead of
a request, and it is why the L1 layer rebuilds the lowerer rather than deleting
it.

One test needs repointing before `form.ts` can go:
`apps/ai-gateway/test/form-contract.test.ts:3` reaches it through a raw relative
path instead of the exports map, and it is the only test that the config form's
parse output satisfies an app's config schema.

## 5. The consolidation this redesign should make

The repository currently carries **four parallel UIs over overlapping product
surfaces**:

1. the console — declared views rendered through one conversion layer (Radix);
2. a React panel under `mantis/src/hosts/webui` (Mantine), ~42k lines, the
   largest single UI in the repo;
3. a vanilla-JS web host under `board/src/hosts/web`;
4. chat cards under `mantis/src/hosts/dingtalk`.

Four implementations of one product is the defect the redesign exists to
remove, and it is also what makes this work tractable: the target is **one
product, one design system, one surface**, with each auxiliary host reduced to
the transport or channel it actually is. The taste skill's own rule — one system
per project, never two in one tree — is the same conclusion reached from the
design side.

**Decided** (the evidence above settles it; this is no longer a direction):

| today | becomes |
|---|---|
| the console at `/console` (Radix Themes) | **the user surface.** The one place a human drives the host. |
| `mantis/src/hosts/webui` (Mantine, ~2.2k lines) | **goes.** Mantis's console is Mantis's app view, like every other app. |
| `board/src/hosts/web` (vanilla JS) | **keeps transport only** — its HTTP API and its MCP endpoint. Its UI is the board's app view. |
| `mantis/src/hosts/dingtalk` | **a channel adapter, not a UI.** Its card *rendering* is presentation and goes; its callback verification is behaviour and stays. |
| `@mantine/core`, `@tabler/icons-react` | **leave the dependency tree.** One system per project: Radix Themes, plus one icon family. |

The 9 app views are not deleted as a *product capability* — they are deleted as
*code*, and reimplemented against the new design. What they declare (screens,
sources, actions, controls) is inventoried in `app-surfaces.md` and
`console-surface.md` beside this file, and that inventory is the ground truth the
reimplementation is held to.

## 6. The design read (fixed before the design step, per the taste skill §0)

*"Reading this as: an operator console for a running agent host, for the
developers and operators who live in it daily, with a Linear-style dark-tech
language, leaning toward `@radix-ui/themes` locked to one appearance + Geist +
a single restrained accent."*

Dials, departing from the landing-page baseline (`8 / 6 / 4`) for the reason §0
gives — every rule is contextual, and this is a product surface, not a page:

| dial | value | why |
|---|---|---|
| `DESIGN_VARIANCE` | **3** | A console is not artsy chaos. The same control looks the same everywhere, or an operator cannot build muscle memory. |
| `MOTION_INTENSITY` | **3** | A surface that is *live* must not animate at the person reading it. Motion marks arrival and nothing else. |
| `VISUAL_DENSITY` | **7** | Cockpit. This is an operator console over fleet state, access decisions and event rings — the data is the product. |

The taste skill's own scope note excludes dashboards and multi-step product UI,
so its landing-page directives (§4.7 hero discipline, §4.8 imagery, §4.9 content
density) do not bind here. Its §4.1–4.5 engineering directives, §5 interactive
states, §9 AI tells and §2 "one system per project" do, and those are what the
reimplementation is designed to.

## 7. The order of work

Deleting 231 files and then rebuilding leaves the tree broken for as long as the
rebuild takes, and it breaks the *proofs* too — a module models a file, and a
file that is gone for a week is a week in which `check:proofs` is red for a
reason nobody can act on. So the deletion and the reimplementation are **one act
per layer**: delete a layer, rebuild it, pass its guards, commit, next.

Each layer is a commit, so any guard that moves is attributable to the layer that
moved it.

| # | layer | deleted | rebuilt as | its gate |
|---|---|---|---|---|
| L1 | **the render contract** — what an app declares and how a node becomes an element | the 10 presentation files and 3 dead files in `packages/effect-ui/src`, `console/view-route.ts`, all of `client/adapt/**` | the new node vocabulary, the new lowerer (§4's extension), the new adaptation layer | `typecheck:client` clean; the client bundle stays near 2.46 MB, not 5.0 |
| L2 | **the shell** — chrome, routing, theme, keyboard | the rest of `apps/effect-server/src/client/**`; `Adapt.lean` and `Stack.lean`, which are dead | per `design-system.md` §10–11 and `flows.md` §6 | the console loads at `/console` and every address in `console-surface.md` §2 still resolves |
| L3 | **the nine app views** | `apps/*/src/effect-ui*.ts` (73 files) | one view per app against the new vocabulary, per `flows.md` §7; `check-ui.ts` updated to the new naming | every app's entry flow walks end to end in a browser; each app's `effect-app.ts` registers cleanly |
| L4 | **the auxiliary hosts** | `mantis/src/hosts/webui/panel` + its `public/`, board `hosts/web/public`, `deckconsole/public` | the board's UI is the board's app view; mantis keeps its HTTP API and loses its panel | mantis and the board still answer over MCP; the board's UI is reachable from the console |
| L5 | **dependencies** | `@mantine/core`, `@tabler/icons-react` | the one icon family chosen in `design-system.md` §8 | `bun run check:boundary` at 0/0 with the packages gone |
| L6 | **proofs** | the dead `Adapt` and `Stack` modules and the 4 `Readout` theorems that model a deleted file | one module per new mechanism, house style | `check:proofs` at **no fewer than 493 in 57** — the pre-deletion figure, not the 460-in-55 floor the deletion leaves |

The `Door`, `Entry` and `Refresh` headers are re-pointed **inside L2**, the layer
that gives them their new subject, not at the end. A module header names the file
it models, so a header left naming a deleted file is the same defect as proving
nothing, and it is exactly the defect this section exists to avoid.

L1 is first because everything else declares against its vocabulary, and because
of the finding in §4: `view-route.ts` is the only producer of `jsonSpec`, so it
cannot go before its replacement exists.

**`scripts/check-ui.ts` is part of the contract, not part of the deletion.** It
enforces five product rules today: no raw `uiHtml` descriptors anywhere in an
app's source; a built-in app must declare `src/effect-ui.ts`; a built-in app
cannot use a raw `*-page/` directory; a built-in app view cannot use
`kind: "embed"`; and every `onPress: "x"` must name an action the view declares.
The last of those is the one that catches a real defect — a control wired to an
action nobody declared does nothing when pressed — so it survives the redesign
and is **updated**, at L3, to whatever the new file naming and vocabulary are.
Deleting it would delete the only thing that refuses a dead control.

All nine apps reach their view the same way, `import { effectUiView } from
"./effect-ui.ts"` in `effect-app.ts`, so L3 cannot delete a view file without
rebuilding the app that registers it. That is the same coupling as L1, one layer
down, and it is why the layers are ordered rather than run in parallel.

Two operational notes that are not visible from a file list:

- `apps/effect-server/src/client-bundle.ts` walks `packages/` for mtimes to
  decide console-bundle staleness, so deleting anything under
  `packages/effect-ui/src` invalidates the built console client even though no
  import edge exists. `bun run --cwd apps/effect-server build:client` must be
  re-run after L1 and L2.
- The live server on 8080 runs without `EFFECT_DEV`, so it serves the
  git-tracked bundle from disk and does not re-read on request. Neither the
  deletion nor the rebuild restarts it; it keeps serving the old console until
  the new bundle is built, which is the intended behaviour and not a failure.
